# AI 托管部署实录：我是怎么把维基百科装进家里的

> 这个项目从头到尾都是 **AI 托管完成**的：用户只提需求、确认关键决策，下载、写代码、配置、调试、验证全部由 AI 助手自动完成。这篇实录记录整个过程的**思路与关键节点**（隐去所有个人信息与路径），给想尝试"AI 时代部署电脑软件"的人一个真实样本。

---

## 一、用户只说了三句话

用户不懂代码，只提了需求，三句话：

1. **我想随时看到维基百科，想看就看**——不是偶尔查，是日常高频使用。
2. **要简体中文**——官方中文版是繁体，看着累。
3. **手机也要能用，全家人用，不要装一堆 App，全程你帮我弄**。

用户补充了一个约束：**不折腾任何网络代理工具**（不想为查资料冒不必要的风险），也**不用国产百科替代**（要的就是维基百科本身）。

## 二、AI 做的第一件事：调研方案（不是直接动手）

AI 没有上来就装，而是先做了方案对比：

| 方案 | 结论 | 原因 |
|---|---|---|
| 浏览器访问在线维基 | 否 | 在线访问本身不稳定，且用户明确不折腾网络工具 |
| 国产百科 App | 否 | 用户明确要维基百科，不要替代品 |
| Kiwix 官方 App（手机端） | 否 | 用户拒绝装 App，要浏览器直接看 |
| Kiwix 桌面离线包 + 浏览器 | **是** | 官方中文离线包（ZIM）含全部中文维基，本地服务，浏览器访问 |
| 镜像站 | 否 | 要账号/验证码，不稳定 |

**关键选型决定**：Kiwix 官方中文 ZIM 包内容是**繁体**。两个转简体路线——客户端 JS 注入 vs 服务端转换——选了**服务端转换**（浏览器零脚本），原因是客户端注入实测会卡死（见下）。

## 三、踩过的两个坑（AI 自己修的）

### 坑 1：客户端 JS 转简体 → 卡死

第一版方案是在浏览器里注入脚本转简体。用户实测：**点第 4 个词条就卡死**，页面无响应。

**AI 的排查与决策**：放弃客户端注入，改为**服务端代理**——在 Kiwix 服务和浏览器之间加一个 182 行的 Python 代理，用 OpenCC 在服务端把繁体转成简体再返回。浏览器收到的就是干净的简体 HTML，零脚本、零注入、零卡顿。

### 坑 2：页面加载后不渲染（CSP 头）

代理上线后出现怪现象：**地址栏在变、页面死活不显示内容**。光看报错根本看不出原因。

**AI 排查过程**：对比浏览器控制台报错 → 发现是内容安全策略（`Content-Security-Policy`）被代理吞掉了 → Kiwix 内容页靠这个头做 iframe 沙箱 → 修复：**安全头必须原样转发**。

### 坑 3：大页面一直转圈（HTTP 长连接）

大词条（1.3MB）打开时浏览器永远转圈。**AI 排查**：HTTP/1.1 keep-alive 转发大响应会截断，浏览器按 Content-Length 死等 → 修复：**每个响应强制 `Connection: close`**。

三个坑都是 AI 从现象出发、查协议、看报错、定位根因后自己修的——用户全程只负责在浏览器里点两下确认"好了/还是卡"。

## 四、验证通过的标准

1. 首页显示简体中文（搜索框、分类导航全简体）
2. 搜索 2.2 万条词条正常
3. 连续跳转多层关联词条不卡
4. 手机连同一 WiFi，浏览器直开局域网地址，效果与电脑一致
5. 断网状态下照常可用

## 五、AI 时代部署电脑软件的通用打法

这次部署提炼出的方法，可以复用到任何"想把某个开源项目跑起来"的场景：

1. **把需求讲清楚，不是讲技术**：说"我要什么效果、谁能用、有什么约束"，不用说自己懂不懂代码。
2. **让 AI 先调研再动手**：方案对比、选型理由，AI 自己查、自己列，你只需要拍板。
3. **AI 自主执行 + 自动修复**：下载、解压、写配置、起服务、验证，一条龙；出 bug 它自己查资料、自己修。
4. **你只做两件事**：确认关键决策（比如"不装 App"）、在它需要时输入密码/确认下载大文件。
5. **验证要可感知**：不是"代码能跑"，而是"手机打开真的能用、断网也能用"。
